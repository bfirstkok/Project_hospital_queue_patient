Lesson 0003 • Configuration Architecture

.env vs Runtime Config
ทำไมสองตัวนี้ถึงดูเหมือนกันเป๊ะ? แต่ทำไมระบบขาดตัวใดตัวหนึ่งไม่ได้?

บทก่อนหน้า: 0002: ผ่าโครงสร้างและหลักการทำ Mock Backend

1. จุดเริ่มต้นของความสงสัย: "ทำไมมันซ้ำซ้อนกัน?"

เมื่อเปิดดูไฟล์ .env: 

PATIENT_API_BASE_URL=http://127.0.0.1:8000
PATIENT_STATUS_REFRESH_MS=10000

แล้วพอเปิดดูไฟล์ runtime-config.ts หรือ runtime-config.js: 

window.PATIENT_APP_ENV = {
  API_BASE_URL: "http://127.0.0.1:8000",
  STATUS_REFRESH_MS: 10000
};

หลายคนจะรู้สึกทันทีว่า "นี่มันข้อมูลชุดเดียวกันชัดๆ! ทำไมไม่เลือกใช้แค่อย่างใดอย่างหนึ่ง?"

🏥 อุปมาเปรียบเทียบ: .env เปรียบเหมือน "พิมพ์เขียวในโต๊ะทำงานของวิศวกร" (มีอยู่ในเครื่องคนสร้าง แต่คนไข้ที่มา รพ. มองไม่เห็น)

runtime-config เปรียบเหมือน "ป้ายบอกทางที่แขวนอยู่หน้าประตูโรงพยาบาล" (เมื่อคนไข้เปิดประตูเข้ามาใน Browser จะมองเห็นป้ายนี้ทันทีว่าเคาน์เตอร์ตรวจอยู่ที่ไหน)

2. มิติเวลา: Build Time (เวลาสร้าง) vs Run Time (เวลาใช้งานจริง)

ความแตกต่างที่แท้จริงไม่ได้อยู่ที่ "เนื้อข้อมูล" แต่อยู่ที่ "ใครเป็นคนอ่าน และอ่านตอนไหน":

มิติ .env (Environment Variables) runtime-config (Runtime Window)
อยู่ที่ไหน? อยู่บนเครื่องคอมพิวเตอร์ของโปรแกรมเมอร์ หรือบนเครื่องเซิร์ฟเวอร์ CI/CD วิ่งไปอยู่บน Browser / มือถือของคนไข้ (ผ่านตัวแปร window)
อ่านตอนไหน? Build Time: อ่านตอนที่โปรแกรมเมอร์สั่ง npm run build Run Time: อ่านทุกครั้งที่คนไข้เปิดหน้าเว็บขึ้นมาดูคิว
บราวเซอร์คนไข้เข้าถึงได้ไหม? ไม่ได้เด็ดขาด ❌ บราวเซอร์ของคนไข้เปิดอ่านไฟล์ .env บนเครื่องเราไม่ได้ ได้ 100% ✅ เพราะถูกโหลดเป็นสคริปต์ runtime-config.js

3. กับดักครั้งใหญ่ของ Next.js Static Export (output: "export")

ในโปรเจกต์นี้ ไฟล์ next.config.ts ตั้งค่าไว้ว่า: 

const nextConfig: NextConfig = {
  output: "export",
  basePath: "/patient",
};

output: "export" แปลว่า Next.js จะคอมไพล์โค้ดทั้งหมดออกมาเป็น HTML/JS ล้วนๆ (Static Site) โดยไม่มี Node.js Server คอยรันอยู่เบื้องหลัง!

ถ้าไม่มี Runtime Config (ใช้ .env เพียวๆ):

Next.js จะ "สลัก (Bake / Hardcode)" ค่า http://127.0.0.1:8000 ฝังตายลงไปในไฟล์ JavaScript ทันทีที่สั่ง build!

ผลร้าย: เมื่อนำไฟล์ไปขึ้นเซิร์ฟเวอร์จริงของโรงพยาบาล (เช่น hospital.bfirstkok.me) เว็บจะพังทันที เพราะมันยังคงพยายามยิงไปที่ 127.0.0.1:8000 บนเครื่องคนไข้เอง! ถ้าอยากเปลี่ยน URL คุณต้องเปิดคอมมาสั่ง npm run build ใหม่ทุกครั้ง!

เมื่อมี Runtime Config (วิถีมืออาชีพ):

โค้ดในหน้าบ้านจะไม่ฮาร์ดโค้ด URL แต่จะเขียนว่า window.PATIENT_APP_ENV.API_BASE_URL

ข้อดี: คุณสั่ง build โค้ดเพียงครั้งเดียว (Build Once) แล้วนำไฟล์ก้อนเดิมไปวางได้ทุกที่! หากต้องการเปลี่ยน API ปลายทาง เพียงแค่เปิดแก้ไฟล์ข้อความ runtime-config.js บรรทัดเดียว ระบบก็เปลี่ยนเป้าหมายทันทีโดยไม่ต้องเสียเวลา build ใหม่!

4. สคริปต์ตัวเชื่อมสะพาน: write-runtime-config.mjs

คำถามคือ: "แล้วทำไมในเครื่องเรา สองตัวนี้ถึงมีค่าเหมือนกัน?"
คำตอบอยู่ที่ไฟล์ scripts/write-runtime-config.mjs ครับ!

เมื่อคุณสั่ง npm run build หรือรันระบบ สคริปต์นี้จะ:

  1. อ่านค่าจาก .env (เช่น PATIENT_API_BASE_URL=http://127.0.0.1:8000)
  2. ตรวจสอบความปลอดภัย (ถ้าไม่ใช่ localhost ต้องเป็น https:// เท่านั้น)
  3. สร้างไฟล์ public/runtime-config.js โดยนำค่าใน .env ไปเขียนลงใน window.PATIENT_APP_ENV ให้แบบอัตโนมัติ!

นั่นเป็นเหตุผลที่คุณรู้สึกว่ามันเหมือนกัน เพราะ runtime-config เป็นผลผลิตที่ถูกสร้างมาจาก .env ในตอนพัฒนานั่นเองครับ!

🧠 ทดสอบความเข้าใจ: ทำไมถึงแยก .env กับ Runtime Config?

สมมติว่าโรงพยาบาลต้องการย้ายระบบขึ้น Production บน Cloudflare หรือ Nginx โดยเปลี่ยน API จาก http://127.0.0.1:8000 ไปเป็น https://api.hospital.com เราควรทำอย่างไรในสถาปัตยกรรมนี้?
