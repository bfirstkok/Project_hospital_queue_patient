Lesson 0001 • Core Mental Model

เข้าใจเบื้องหลังและการทำงานของ API
ทำไมต้องออกแบบ ใช้งาน เขียน และส่งข้อมูลแบบนี้?

เป้าหมาย: สร้างความเข้าใจเชิงเหตุผลและภาพจำลองในหัว (Mental Model) ให้กระจ่างแจ้ง ก่อนที่เราจะแตะโค้ดแม้แต่บรรทัดเดียว

1. ภาพจำลองตั้งต้น: API คืออะไรในโลกจริง?

คำว่า API (Application Programming Interface) ฟังดูเป็นศัพท์เทคนิคที่น่ากลัว แต่ถ้าเราถอดเปลือกนอกออก API ทำหน้าที่เหมือน "เคาน์เตอร์เวชระเบียน" หรือ "บริกรในร้านอาหาร"

🏥 อุปมาเทียบกับระบบโรงพยาบาล: คนไข้ (Frontend / Client) เดินเข้ามาในโรงพยาบาล ไม่ได้รับอนุญาตให้เดินดุ่มๆ เข้าไปในห้องเก็บแฟ้มประวัติผู้ป่วย (Database) เอง หรือหยิบยาในคลังเองเด็ดขาด!

สิ่งที่คนไข้ทำได้คือ เดินไปที่ เคาน์เตอร์บริการ (API Endpoint) บอกเจ้าหน้าที่ว่าต้องการอะไร พร้อมยื่นบัตรประชาชน (Request Header / Payload) จากนั้นเจ้าหน้าที่เคาน์เตอร์ (Backend Handler) จะตรวจสอบความถูกต้อง เดินไปค้นแฟ้มหลังห้อง (Database Query) แล้วเดินกลับมาพร้อม "ใบนำทางหรือบัตรคิว" (Response) ยื่นให้คนไข้

ทำไมโลกการเขียนโปรแกรมถึงสร้างเคาน์เตอร์นี้ขึ้นมา? ทำไมมือถือของคนไข้ไม่ต่อตรงกับ Database ไปเลยให้จบๆ?

2. ทำไมต้องออกแบบแบบนี้? (Why Design It This Way?)

1. ความปลอดภัยขั้นวิกฤต (Security Boundary)

ถ้ารหัสผ่านเข้า Database ฝังอยู่ใน Browser หรือมือถือ ทุกคนที่กด F12 Inspect จะเห็นรหัสผ่านทันที และสามารถสั่ง DROP TABLE patients; ได้ API จึงเป็น "กำแพงปราการด่านเดียว" ที่มีสิทธิ์คุยกับฐานข้อมูล

2. กฎเกณฑ์ทางธุรกิจ (Business Rules)

คนไข้จะกดขอคิวได้ ต้องผ่านการคัดกรอง หรือไม่ติดคิวซ้ำซ้อน กฎเหล่านี้ต้องถูกบังคับที่ Backend Server เสมอ เพราะโค้ดฝั่ง Client สามารถถูกแฮกหรือปลอมแปลงได้ง่ายดาย

3. ความเป็นอิสระ (Separation of Concerns)

Frontend อาจเปลี่ยนจาก Next.js เป็น Mobile App (Flutter/iOS) หรือตู้คีออสจอสัมผัส แต่ทุกคนคุยกับ "API เส้นเดิม" ได้ทันทีโดยไม่ต้องเขียนตรรกะระบบใหม่

4. ความไม่จำสถานะ (Statelessness)

Server ไม่ต้องจำว่า "เมื่อ 5 วินาทีก่อนเครื่องนี้ทำอะไร" ทุก Request ที่ส่งมาต้องพกข้อมูลระบุตัวตนมาครบในตัว ทำให้เราเพิ่ม Server เป็น 10 เครื่องเพื่อรองรับคนไข้หมื่นคนพร้อมกันได้ทันที (Scalability)

3. ทำไมต้องใช้งานแบบนี้? (Why Consume It This Way?)

การใช้งาน API ถูกออกแบบเลียนแบบ "ไวยากรณ์ภาษาคน" ที่ประกอบด้วย คำกริยา (Verb) + คำนาม/สิ่งของ (Noun)

HTTP Method (กริยา) เจตนาของการใช้งาน ตัวอย่างในระบบโรงพยาบาล ลักษณะสำคัญ
GET "ขอดู / ขอดึงข้อมูล" ไม่เปลี่ยนแปลงข้อมูล GET /api/queue/status ดึงกี่ครั้ง ข้อมูลใน DB ก็ไม่เปลี่ยน (Safe)
POST "สร้างสิ่งใหม่ / ยื่นคำร้องใหม่" POST /api/queue/register กดย้ำๆ อาจสร้างคิวซ้ำ ต้องระวัง
PATCH / PUT "แก้ไขข้อมูลบางส่วน / แทนที่ข้อมูลเดิม" PATCH /api/patients/me อัปเดตเฉพาะเบอร์โทรศัพท์หรือที่อยู่
DELETE "ขอลบหรือยกเลิกทรัพยากร" DELETE /api/queue/ticket ขอยกเลิกบัตรคิวตรวจ

เหตุผลที่ต้องแบ่งชัดเจน: เครือข่ายอินเทอร์เน็ต (รวมถึงบราวเซอร์และระบบแคช) รู้ว่าถ้าเป็น GET สามารถแคช (Cache) เก็บไว้ได้เพื่อความเร็ว แต่ถ้าเป็น POST ห้ามแคชเด็ดขาดเพราะข้อมูลอาจเสียหาย

4. ทำไมต้องส่งข้อมูลแบบนี้? (Why Transport Data This Way?)

เวลาเราส่งคำขอทาง HTTP มันเหมือน "การส่งพัสดุหรือจดหมายลงทะเบียน" ที่แยกส่วนอย่างชัดเจน:

1. ซองจดหมายด้านนอก (Headers)

เป็นข้อมูลกำกับการจัดส่ง (Metadata) ไม่ใช่เนื้อความจดหมาย เช่น:
• Content-Type: application/json (บอกว่าข้างในเขียนด้วยภาษา JSON นะ)
• Authorization: Bearer xyz... (แปะบัตรประชาชนหรือตั๋วอนุญาตว่าใครเป็นคนส่ง)

2. สิ่งของในกล่องพัสดุ (Request Body)

เนื้อหาข้อมูลจริงที่ต้องการส่งมอบ เช่น ฟอร์มข้อมูลผู้ป่วย: ชื่อ, นามสกุล, อาการเริ่มต้น, เบอร์ติดต่อ

ทำไมโลกถึงเลือกใช้ JSON (JavaScript Object Notation)?

ในอดีตโปรแกรมเมอร์เคยส่งข้อมูลด้วย XML หรือข้อความดิบ (Plain Text) แต่ JSON ชนะขาดลอยเพราะ 3 เหตุผล:

  1. มนุษย์อ่านรู้เรื่อง และคอมพิวเตอร์แปลงได้ทันที: โครงสร้าง Key-Value {"hn": "HN-67001", "age": 35} ตรงกับ Object ในแทบทุกภาษาบนโลก (Python Dict, JS Object, Swift Dictionary)
  2. มี Data Type ติดมาด้วย: แยกความต่างระหว่างตัวเลข 35 กับข้อความ "35" และ boolean true/false ชัดเจนโดยไม่ต้องเขียนโปรแกรมแกะเอง
  3. น้ำหนักเบา (Lightweight): ไม่มี Tag เปิด-ปิด ยืดยาวเหมือน XML ทำให้กินเน็ตมือถือน้อยลง ส่งผ่าน 4G/5G เร็วขึ้น

5. ทำไมต้องเขียนแบบนี้? (Why Implement & Structure It This Way?)

เวลาเขียนโค้ด Backend ทำไมเราไม่แค่รับค่ามาแล้วยัดลง Database เลย? ทำไมต้องมีสถาปัตยกรรมแบบ "Controller / Handler -> Validation -> Business Logic -> Data Access"?

เพราะ API คือ "สัญญาประชาคม (Contract)" ระหว่างสองฝั่งที่ไม่เคยเห็นหน้ากัน:

  • กฎเหล็กความปลอดภัย (Never Trust Client Input): คนร้ายสามารถยิงคำขอปลอมเข้ามาได้ Backend ต้องมีด่านตรวจ (Validation) เสมอ เช่น เลขบัตรต้องครบ 13 หลัก, PIN ต้องเป็นตัวเลข 6 ตัว
  • รหัสสถานะสากล (HTTP Status Codes): แทนที่จะตอบกลับมาแบบกำกวม API สากลสื่อสารด้วยรหัส 3 หลักที่ระบบอัตโนมัติเข้าใจได้ทันที:
    • 200 OK / 201 Created: สำเร็จ เรียบร้อย
    • 400 Bad Request: ลูกค้ากรอกข้อมูลผิดพลาด
    • 401 Unauthorized: ไม่ได้เข้าสู่ระบบ / ไม่มีสิทธิ์
    • 404 Not Found: ไม่พบคิวหรือผู้ป่วยที่ระบุ
    • 500 Internal Server Error: เซิร์ฟเวอร์พังข้างใน
🧠 ทดสอบความเข้าใจ (Self-Check Challenge)

สมมติว่าคนไข้ต้องการ "ขอยกเลิกบัตรคิว" ในระบบโรงพยาบาล ตามหลักการออกแบบ API ที่ดี คุณคิดว่าควรออกแบบอย่างไร?
